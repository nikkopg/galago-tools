<objective>
Close the one gap in 02-VERIFICATION.md (CR-01): `Resume()`'s crash-recovery branch in
`tools/fast/server.py` still decides "did the instrument accept the resume" with its own inline
errorCode comparison instead of `_accepted()`, so a malformed reply such as `{"errorCode": False}`
(`False == 0` in Python) is credited as accepted and the adapter waits on a run that was never
resumed. This plan routes that check through `_accepted()`, adds the regression tests the gap names
(a `{"errorCode": False}` reply and a reply with no errorCode on this exact branch must not reach
`service.wait` and must return the rejection), pins the full acceptance boundary on that path, and
corrects `_accepted()`'s docstring, which states a fixed number of call sites.

This is the crash-recovery half of ADP-04, inside this phase's `Resume` (D-07/D-08 scope). It
protects LIVE-02's "ends with the run's real outcome" on that path.

Scope decisions (stated explicitly, as the gap-closure brief requires):
- **WR-02 (`_is_no_error`'s loose comparison) is NOT included.** It is not in VERIFICATION.md's
  `gaps:`. The function came from Phase 3 commit 201d987 and its open disposition is tracked in
  Phase 3's 03-REVIEW-DISPOSITION.md (STATE.md, Blockers/Concerns). It only decides whether the
  instrument's outcome text is appended to the Aborted message. That wording is D-09 (costly
  reversibility, galago-core shows it verbatim), and changing it needs its own wording decision for
  a malformed outcome. It does not decide whether a command was accepted or whether the adapter
  waits. Task 1's acceptance proves `_is_no_error` is unchanged.
- WR-03 and IN-01 are out of scope (scripts/ files, not this phase's).
- No new rule is added to `_adapter_invariant_violations` (D-17: the AST checks need no new rules).
  The single-definition truth is enforced by this plan's AST acceptance command and by the
  behavioural regression tests.
- Tests use the real core over a stub transport (D-14). `service.wait` is spied with
  `patch.object(..., wraps=...)`, not replaced, so "does not proceed to service.wait" is observed
  on the real `FastService`.

Purpose: an operator who sends Resume after a crash gets the instrument's rejection back right away
when the instrument did not really accept, instead of a step that waits on a run that never resumed.

`_resume_with_reply` and `_assert_rejected_without_waiting` helpers and 3 tests in
`tools/tests/fast_test.py`.
