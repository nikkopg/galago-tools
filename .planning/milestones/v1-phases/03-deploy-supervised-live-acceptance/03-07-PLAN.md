<interfaces>
Read-only observation (same as plan 03-04): scripts/fast_status.py, the post-deploy F.A.S.T.log, journalctl, MainPID.
Design section 8: when galago-web restarts while a step runs, the gRPC call is dropped; the adapter's handler thread keeps
  waiting and holds the motion lock; the queue has no running step afterwards, so the run page shows no control bar; the tool
  page's control commands still work because they do not take the motion lock; the lock clears when that wait ends.
tools/fast/server.py Resume: a non-blocking _motion_lock acquire fails while the Transfer runs, so Resume calls service.resume
  and returns on acceptance (no wait); the original Transfer's own wait reports the outcome. base_server sets READY in the
  Transfer's finally, after the motion lock is released.
galago-core: the tool page's recoveryControl uses Tool.forId (no Configure needed after a restart); RunRecoverySection enables
  Resume/Abort when no run step tracks the tool. galago-web never relaunches tool processes (the manager page on 8081 does).
base_server.Configure sets READY after a real Configure, so Connect, the Simulate switch or "Connect all tools" while the
  orphaned Transfer waits would flip BUSY to READY.
Proposed transfer (D-10, operator decides): one F.A.S.T Transfer source_deck 1, dest_deck 3, source_plate_id 1,
  dest_plate_id 1, A4 to A4 (column 4), num_rows 8, num_cols 1, volume 50, tip_reuse fresh, expected_tray_id blank.
