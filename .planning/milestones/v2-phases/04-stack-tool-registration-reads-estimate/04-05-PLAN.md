<assumption_delta_decision>
Detector signal: pluralization ("another command holds the tool BUSY", ROADMAP SC 5).
- Primary noun: the single motion command that holds base_server's BUSY status. It stays the only
  thing that owns tool status; reads are a stateless side channel that never owns or flips status.
- Decision: no-change. Rationale: promoting a multi-command status model would mean editing
  tools/base_server.py (forbidden by D-13) and would loosen motion serialisation; the bypass adds
  reads alongside the one status owner without contradicting it. The second front end (stack-mcp vs
  galago) is already modelled by the core's endpoint_key owner lock (Plan 02), which is unchanged.
- Companion invariant test (accepted, in this plan): TestBusyReads iterates every READ_COMMANDS
  entry while a non-read holds BUSY, and TestReadCommandSet pins the set so a motion or acknowledge
  command can never join it silently.
</assumption_delta_decision>
